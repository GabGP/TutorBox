# Qwen3-TTS Engine Profile (Primary Winner)

## Architectural Profile

- **Model**: `Qwen3-TTS-12Hz-1.7B-Base`, quantized to GGUF `Q4_K_M` for local inference.
- **Architecture**: 1.7B autoregressive speech model paired with a 12 Hz neural audio codec/vocoder.
- **Runtime**: `llama-tts` from `llama.cpp`, with `-ngl 99` requesting GPU layer offload.
- **Target Language**: Spanish is supported natively by Qwen3-TTS; the backend passes `--tts-lang es`.
- **License**: Apache 2.0 model family.
- **Output**: 24,000 Hz, 16-bit mono PCM WAV.
- **Model Assets**: `Qwen3-TTS-12Hz-1.7B-Base-Q4_K_M.gguf` plus its `mmproj-Qwen3-TTS-12Hz-1.7B-Base-Q8_0.gguf` projector.

The integrated backend is explicitly named `qwen3-tts`. “GGUF” describes the local weight format; it is not a separate engine selection anymore.

## CUDA Verification & Latency Interpretation

The local workstation's `llama-tts --list-devices` reports `CUDA0: NVIDIA GeForce RTX 5060 Ti`, and a verbose synthesis run reports `using device CUDA0`, CUDA graph warm-up, and CUDA compute buffers. The benchmark CSV's Qwen row is therefore GPU-backed. The provider column is now generated by probing `llama-tts --list-devices`, rather than assuming CPU for unknown engines.

Qwen is slower than Sherpa-ONNX/Piper even on CUDA because it generates codec tokens autoregressively and then runs a neural vocoder. The current `llama-tts` integration is a one-shot subprocess, so each uncached synthesis also pays process/model startup. This is the quality winner so far, not the latency winner.

## Voices

The deployed checkpoint is the **Base** model. It does not expose a fixed named-speaker catalog; the API consequently reports one `base-default` voice. Base is intended for rapid voice cloning from a reference recording, but the current `llama-tts` backend does not yet wire a reference-audio setting into TutorBox.

The official Qwen3-TTS **CustomVoice** checkpoints provide these nine named speakers: `Vivian`, `Serena`, `Uncle_Fu`, `Dylan`, `Eric`, `Ryan`, `Aiden`, `Ono_Anna`, and `Sohee`. They can speak supported languages, although Qwen recommends each speaker's native language for best quality. Moving TutorBox to a CustomVoice GGUF would require matching model assets and a speaker argument; those names are not available in the current Base deployment. See the [official Qwen3-TTS speaker list](https://github.com/QwenLM/Qwen3-TTS#custom-voice-generate).

## Binary Discovery & Configuration

`TTS_QWEN_BINARY` is optional. When empty, TutorBox searches next to the selected model, common Windows/Linux installation locations, and `PATH`; a normal installation is therefore sufficient when it exposes `llama-tts` to `PATH` or uses one of those standard locations. TutorBox does not recursively scan the entire PC. Set `TTS_QWEN_BINARY` when the executable is installed in a non-standard directory.

`TTS_QWEN_GGUF_PATH` can point to the model file or its containing directory. When it is empty, TutorBox searches the project cache and the configured appliance model directory. `TTS_QWEN_THREADS` controls CPU-side prompt/host work; `-ngl 99` remains the GPU-offload request.

## Dependency & Harness Decision

No new Python dependency is required for the integrated Qwen backend. It uses the Python standard library to invoke the existing external `llama-tts` binary; the existing `piper-tts`, `sherpa-onnx`, and `onnx` dependencies remain unchanged. The Qwen GGUF/projector files and a CUDA-capable `llama-tts` build are runtime assets, not `pyproject.toml` dependencies.

The former standalone `harness_qwen.py` duplicated the engine and could report a provider from the requested `ngl` value without verifying the device. It is removed; use the integrated benchmark path above. `harness_melo.py` remains as a reference for the rejected MeloTTS experiment.
